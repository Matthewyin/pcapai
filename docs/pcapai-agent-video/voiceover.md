# pcapAI Agent 口播稿 v1

网络排障里，最麻烦的往往不是没有抓包。

而是抓包太多，位置不同，时间不齐。
客户端一份，负载均衡前后一份，服务端一份。
中间还可能有 NAT、代理、SSL 卸载、地址改写。

这时，单看一个 pcap 很容易得出局部结论。
但真正的问题是：这些证据能不能串起来？

pcapAI Agent 要解决的，就是这个问题。

它不是一个简单的“问答机器人”。
也不是让大模型直接猜故障原因。

它的设计原则是：能确定的，先用确定性工具确定。
需要解释的，再交给 Agent 组织语言和推理。

用户上传 pcap 后，系统会先建立一个 case graph。
每一次提问都会形成一个 QueryRun。
这个 QueryRun 记录问题、过滤条件、候选通信对、诊断项、证据卡和路径关系。

在后端，Chain Planner 会判断这个问题应该怎么拆。
如果是 TCP、DNS、TLS、HTTP、ICMP、UDP 这类明确问题，
协议适配器会直接调用 tshark 查询数据包。

RST、重传、Zero Window、DNS 失败、TLS Alert、HTTP 5xx，
这些都不需要模型猜。

如果问题需要多步分析，执行引擎会按步骤运行。
前一步产生的结果，可以绑定到后一步继续查询。
每一步之后，case graph 都会刷新，保证后续分析读到的是最新证据。

当确定性证据已经生成，Agent 再介入。
它通过 case-graph MCP 读取案件上下文，
通过 tshark-query MCP 查询原始数据包，
最后给出中文解释、置信度、缺失上下文和下一步建议。

pcapAI 的关键价值，是把结论和证据绑定在一起。

每张证据卡都能落到 pcap 文件、display filter、frame number。
用户可以一键打开 Wireshark，回到原始数据复核。
这意味着结论不是一段看起来合理的话，而是一条可以检查的证据链。

看一个典型场景。

用户上传多节点抓包，然后问：为什么这次访问失败？

pcapAI 会先找到候选 TCP session，
再检查握手、RST、重传、窗口、双向流量和关闭状态。
如果路径上只有上游看到访问，下游没有对应会话，
系统会提示可能存在断点，或者需要补充 NAT、代理、时间偏移信息。

如果发现 RST 或重传集中在某一段，
证据卡会直接给出对应通信对和过滤器。
用户点开后，就能在 Wireshark 里看到同一组包。

最后，Agent 会把这些证据整理成可读结论：
问题更可能出现在哪一段，
当前证据能证明什么，
还有哪些信息不能确认。

所以 pcapAI Agent 的价值，不是替代工程师判断。
而是把分散的 pcap、过滤器、协议事件和排障经验，
收束成一次可追溯、可复核、可继续追问的分析流程。

结论可读。
证据可点。
路径可复核。

这就是 pcapAI Agent。
